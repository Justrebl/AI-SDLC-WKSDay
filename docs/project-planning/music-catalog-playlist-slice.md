## Executive Summary

The playlist slice lets a listener browse the Music Catalog and collect tracks into a single playlist during one session. The value is a **hypothesis**: selected tracks stay together, so the listener can see their choices without repeatedly scanning the full catalog. It has not been measured and no listener research supports it.

Target users are hypothesized listeners (not researched). Scope is deliberately small: one playlist, in-memory state only, and none of users, authentication, persistence, reorder, remove, search, or playlist creation.

The primary success metric is BG-001 as carried from the BRD: 6 of 10 testers add at least one track and score the playlist at least 4 out of 5 on average across two post-session questions, by end of year (baseline: none; owner: TPM). Release horizon: a single workshop slice delivered on the existing .NET 10 minimal API and React 19 + Vite front end.

Source: approved BRD `docs/project-planning/music-catalog-playlist-slice-brd.md` (v1.0.0, sha256 `3138dd21...556b8`, signed off under waiver WV-001) and delivery brief `docs/project-planning/playlist-design-decisions.md`.

## Functional Requirements

- `FR-001`: A listener can browse the track catalog.
  - Actor: Listener. Trigger: Opens the application. Outcome: Catalog tracks are visible.
  - Acceptance Criteria: AC-001. Product Goals: GOAL-001. Priority: MUST. BRD: FR-001.
- `FR-002`: A listener can add a catalog track to the single playlist.
  - Actor: Listener. Trigger: Chooses to add a track. Outcome: The track appears in the playlist, visible alongside the catalog.
  - Acceptance Criteria: AC-002. Product Goals: GOAL-001. Priority: MUST. BRD: FR-002.
- `FR-003`: Adding a track already in the playlist is rejected with visible feedback and an HTTP 409 response.
  - Actor: Listener. Trigger: Adds a duplicate. Outcome: The playlist is unchanged, the API responds with HTTP 409, and the listener sees the inline message in DD-003.
  - Acceptance Criteria: AC-003, AC-004. Product Goals: GOAL-001. Priority: MUST. BRD: FR-003.
- `FR-004`: An empty playlist shows a visible empty state: "Your playlist is empty. Add a track to get started."
  - Actor: Listener. Trigger: Views the playlist with no tracks. Outcome: Empty-state message visible.
  - Acceptance Criteria: AC-005. Product Goals: GOAL-001. Priority: MUST. BRD: FR-004.
- `FR-005`: Adding a track id that is not in the catalog is rejected with an HTTP 404 response and the playlist is unchanged.
  - Actor: Listener (via the front end) or API client. Trigger: Adds an unknown track id. Outcome: HTTP 404; the playlist is unchanged.
  - Acceptance Criteria: AC-008. Product Goals: GOAL-001. Priority: MUST. Source: delivery brief (`docs/project-planning/playlist-design-decisions.md`).

## Constraints

- `CON-001`: One playlist only. Category: scope. Non-negotiable for this slice. Source: requester scope (BRD CON-001).
- `CON-002`: State is held in memory only; no database, file writes, or external services. Category: technical. Source: requester scope (BRD CON-002). Non-negotiable for this slice.
- `CON-003`: Out of scope: users, authentication, persistence, reorder, remove, search, and playlist creation. Category: scope. Source: requester scope (BRD CON-003). Non-negotiable for this slice. This bundles seven exclusions; they stay one constraint (accepted 2026-10-07) and are listed individually as non-goals in MVP framing.
- `CON-004` (PRD-added from delivery brief; accepted 2026-10-07): The slice uses the shared delivery contract: `GET /api/tracks`, `GET /api/playlist`, `POST /api/playlist/tracks` with JSON body `trackId`. Non-negotiable for this slice. Status-code behaviour is specified in FR-003 and FR-005. Category: technical. Source: `docs/project-planning/playlist-design-decisions.md`. Platform: .NET 10 minimal API under `/api`, React 19 + Vite front end.

## Acceptance Criteria

All criteria are **not yet demonstrated**.

- `AC-001`: Given the catalog has tracks, When a listener opens the application, Then the tracks are visible. Covers: FR-001. Status: Not Started.
- `AC-002`: Given a track not in the playlist, When the listener adds it, Then it appears in the playlist. Covers: FR-002. Status: Not Started.
- `AC-003`: Given a track already in the playlist, When the listener adds it again, Then the API responds with HTTP 409 and the playlist does not gain a second entry. Covers: FR-003. Status: Not Started.
- `AC-004`: Given a duplicate add is rejected, When the rejection occurs, Then the inline message "This track is already in your playlist." is shown. Covers: FR-003. Status: Not Started.
- `AC-005`: Given the playlist has no tracks, When the listener views it, Then the empty state is visible. Covers: FR-004. Status: Not Started.
- `AC-006`: Given the catalog and playlist controls, When assessed by role and label and operated by keyboard only, Then each control has an accessible role and label, is keyboard-operable with a visible focus indicator, and the duplicate-add message exposes `role="alert"`. Covers: NFR-001. Status: Not Started.
- `AC-007`: Given the implementation, When the API (xUnit) and front-end (Vitest) tests run, Then they pass, including checks that AC-003 and AC-008 are covered by automated tests. Covers: NFR-002. Status: Not Started.
- `AC-008`: Given a track id that is not in the catalog, When it is added to the playlist, Then the API responds with HTTP 404 and the playlist is unchanged. Covers: FR-005. Status: Not Started.
